第 1 课：Skill 设计的第一性原理

把 AI 的选择空间收窄 —— 好的 skill 不是百科全书，而是一组约束

📅 2026-06-14 ⏱ ~20 分钟 🎯 Mission →

1. 从一个问题开始

你有两个 skill，都写得结构完整、有检查清单、有渐进式披露。但你仍然觉得「有所不足」。

让我们直面这个问题：两个结构相似的 skill，为什么一个稳定可靠，另一个总跑偏？

核心洞察：AI 在每一步都有近乎无限的选择空间。一个好的 skill，本质上是一个约束引擎——它在每一步都刻意把 AI 的选择空间收窄，直到只剩下你想要的那个答案。

反过来说：如果你的 skill 在某一步给了 AI 太多的「发挥空间」，那 AI 就会发挥——而且往往发挥的不是你想要的。

2. Skill 质量三角

一个 skill 的质量可以从三个维度评估：

T Trigger Precision（触发精度） — AI 能准确知道什么时候该用这个 skill 吗？有没有明确的和不触发的情况？

P Procedure Clarity（流程清晰度） — 每一步是否只有一个明确的行动？AI 读完这一步知道具体要做什么吗？

G Guardrails（护栏完整度） — 哪些事绝对不能做？出错/信息不足/超出范围时怎么办？

🔍 用一个比喻来理解：skill = 驾驶导航

假设你要开车去一个陌生的地方：

  • Trigger = 你知道什么时候该打开导航（不是每次出门都用，但去陌生地方一定用）
  • Procedure = 导航的每一步指令：「前方 300 米右转」——明确、单一、不可误解
  • Guardrails = 「如果错过了路口，不要掉头，前方 500 米有替代路线」——出错后有预案

一个差的导航：「你往西北方向开，自己找路」——这就是一个 Procedure 不清晰的 skill。

3. 诊断你的 skill：一个实例

下面是你 study-note skill 的第 1 步原文：

### 第 1 步：搜索获取知识
针对用户问题，通过网络搜索获取知识。规则见 `references/note-rules.md`。

用三角框架来诊断：

⚠️ 当前的问题

Procedure 不够清晰：「通过网络搜索获取知识」是一个大方向，不是一步操作。AI 要搜什么？用什么搜？搜到什么程度算够？搜完了怎么处理结果？

「规则见 references/XXX」把具体的约束推到了另一个文件——但那个文件是写给人看的规则，不是写给 AI 的操作指令。

✅ 改进方向

拆成 2-3 个更小的子步骤，每个步骤只有一个明确行动：

1a. 提取搜索关键词
1b. 用 WebSearch 搜索（1-2 次）
1c. 对关键结果用 WebFetch 获取详情
1d. 判断信息是否足够 → 不够则补充搜索

🔍 但我每个步骤都拆了呀？为什么还是感觉不够？

因为你拆的粒度是对的（第 0-5 步），但是每一步内部的具体操作动作可以更精确。比较：

  • 「搜索获取知识」 ← 一个方向
  • 「从用户问题中提取 3-5 个关键词，用 WebSearch 逐一搜索」 ← 一个动作
  • 「对搜索结果中排名前 3 的页面用 WebFetch 获取全文」 ← 一个动作
  • 「如果 WebFetch 返回的内容加起来不足 500 字，再搜索一次」 ← 一个带判断的动作

每一步的「动作」越具体，AI 的发挥空间越小，结果越可控。

4. 三角框架详解

4.1 Trigger Precision（触发精度）

一个好 trigger 需要同时说清楚两件事：

  • 什么时候触发（正面条件）
  • 什么时候不触发（排除条件）

看看你 feynman-test 的 description：

当用户要求「用费曼学习法测试」...时使用此 skill。
即使用户没说"费曼"这个词，只要表达了检验自己理解程度的意图...也应该触发。
普通的「XX 是什么」「帮我解释」「帮我复习」不触发。 ← 这就是排除条件

最后一句排除条件非常关键——它防止了误触发。这正是好的 Trigger Precision。

4.2 Procedure Clarity（流程清晰度）

判断标准：一个没看过你 skill 的人，读完某一步后，能不能不加思考地执行？

常见问题：

  • 动词模糊：「分析」「处理」「整理」← 这些不是操作
  • 隐含判断：「选择合适的方法」← 什么叫合适？AI 不知道你的标准
  • 引用外跳：「详见 XX 文档」← 那个文档足够具体吗？
🛠 实操技巧：把「动词」换成工具名

把模糊动词替换成 AI 可执行的具体动作：

  • 「搜索」→ WebSearch("关键词") 或 Grep("pattern")
  • 「检查」→ Read(file_path) 然后逐项对照 checklist
  • 「确认」→ AskUserQuestion(...) 等待用户回复
  • 「写入」→ Write(file_path, content)

你的 skill 已经有了这种意识——比如 study-note 第 0 步写了「用 Grep 按概念关键词搜索」。这就是好的 Procedure Clarity。

4.3 Guardrails（护栏完整度）

护栏回答三个问题：

  1. 绝对不能做什么？（硬约束）
  2. 信息不足时怎么办？（兜底策略）
  3. 出错了怎么恢复？（错误处理）

你 study-note skill 里已经有了很好的护栏例：

  • 「不得自动修改已有 MOC」← 硬约束
  • 「多文件必须列出完整清单，等用户确认」← 兜底策略
  • 「无敏感信息（密码/密钥/Token）」← 安全检查
一个实用的护栏 checklist：每次写完 skill，问自己——如果 AI 在这一步做了最蠢的事，我的 skill 里有东西能拦住它吗？

5. 动手练习

✏️ 练习：用三角框架评估你自己的 skill

打开你的 study-note SKILL.md，用这个 checklist 逐项检查：

  • Trigger：有没有说清楚不触发的情况？
  • Trigger：和其他 skill 的触发条件有重叠吗？重叠时 AI 怎么选？
  • Procedure：每一步是不是只有一个明确的动作？
  • Procedure：有没有「分析」「处理」「整理」这种模糊动词？
  • Guardrails：如果搜索不到结果，skill 告诉 AI 该怎么办了吗？
  • Guardrails：如果用户拒绝了确认，skill 有退路吗？

💡 在纸上或笔记里写下你找到的 1-3 个可以改进的点。下一课我们会基于这些点来实际改写。

6. 关键收获

本课核心：
1. 一个好 skill = 一个约束引擎，每一步都在收窄 AI 的选择空间
2. 用 T-P-G 三角（Trigger / Procedure / Guardrails）来诊断任何 skill
3. 动词模糊 = 选择空间大 = 结果不可控，把动词换成具体的工具调用
4. 护栏不是锦上添花——它是 skill 从「能用」到「可靠」的关键一跳
