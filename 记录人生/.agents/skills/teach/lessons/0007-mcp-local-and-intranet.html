第 7 课：MCP 在内网

MCP Server 默认就跑在你机器上——不需要外网

📅 2026-06-14 ⏱ ~15 分钟 ← 第 6 课

1. 你可能搞混了一件事

你说「内网难以连接外网的 MCP server」——这句话隐含了一个假设：MCP server 是部署在外网的。

事实：MCP server 默认运行在本地（localhost）。它不是远端的云服务，是你本机上的一个进程。你不需要连接任何外网就能使用自己写的 MCP 工具。

2. MCP 的真实架构

你的机器

AI (Claude/Copilot)

↕ MCP 协议

MCP Client

↕ (stdio / localhost HTTP)

MCP Server ← 本机进程

↕

你的文件 / 内网数据库 / 内网 API

全部在本地/内网

整个链路中唯一需要网络的是：AI 模型本身的 API 调用（你已经在用了）。MCP server 到 MCP client 的通信走的是 stdio（标准输入输出）或 localhost，不经过外网。

3. 两种 MCP Server 运行方式

方式通信在哪里例子
stdio 标准输入/输出（管道） MCP client 直接启动 server 子进程 你的 ide MCP 工具就是这种方式
HTTP localhost HTTP 请求 独立进程监听本地端口 需要持久状态的服务（如数据库连接池）

两种方式都不需要外网。stdio 方式甚至不需要网络——它是进程间管道通信。HTTP 方式走 127.0.0.1，不离开本机。

4. 内网环境下你可以做什么

MCP server 运行在你本机，但它可以连接你能访问的任何资源：

场景MCP Server 做什么网络要求
查内网 GitLab/Jira/Confluence 调内网 API，封装成 MCP 工具 你的机器能访问内网就行
查内网数据库 连接内网 DB，暴露查询接口 同上
操作本地文件 读写本机文件系统 零网络
调用内网 CI/CD 触发 Jenkins/流水线，取结果 你的机器能访问 Jenkins 就行
代码静态分析 运行本地 linter/工具，返回结构化结果 零网络
核心原则：MCP server 需要的网络权限 = 你自己访问那个资源需要的网络权限。你在内网能访问的，MCP server 就能访问。你不能访问的（外网），它也不需要——因为你的数据在内网。

5. 内网 MCP 的实际例子

假设你内网有一个代码审查工具，API 在 http://internal-review.company.com/api。你可以写一个 30 行的 Python MCP server：

# mcp_review_server.py（部署在你的机器上，不到外网）
import requests
from mcp.server import Server, Tool

server = Server("code-review-tools")

@server.tool()
def get_pending_reviews(user: str) -> list:
    """获取某人待审查的 MR 列表"""
    resp = requests.get(
        "http://internal-review.company.com/api/reviews",
        params={"reviewer": user}
    )
    return resp.json()

@server.tool()
def get_review_diff(review_id: str) -> str:
    """获取某个 MR 的完整 diff"""
    resp = requests.get(
        f"http://internal-review.company.com/api/reviews/{review_id}/diff"
    )
    return resp.text

server.run()  # 监听 stdio

然后在 Claude Code 配置中注册：

// .claude/mcp.json
{
  "mcpServers": {
    "code-review": {
      "command": "python",
      "args": ["./mcp_review_server.py"]
    }
  }
}

现在 AI 就能调用 get_pending_reviews 和 get_review_diff——全程不经过外网。

6. 对比：CLI 也能调内网 API，为什么要 MCP？

这回到第 6 课的决策框架。但内网场景多了一个因素：稳定性。

CLI（curl / PS 脚本）MCP
认证处理每次让 AI 写 token 处理逻辑在 server 中封装一次
错误处理AI 解析 HTTP 状态码和 bodyserver 返回结构化错误
API 变更AI 不知道 API 已升级，用旧参数修改 server 代码，AI 无感知
分页/限流AI 自己处理，容易漏在 server 中处理，透明
内网场景下 MCP 的额外价值：内网 API 往往没有好的文档、没有 SDK、认证方式不标准。CLI 脚本处理这些边缘逻辑时很容易出错。MCP 把脏活封装在 server 里，AI 只看到干净的接口。

7. 什么情况下内网 MCP 不值得做

不是所有内网工具都值得封装成 MCP：

不值得值得
只在一个 skill 中用，且调用很简单在 2+ 个 skill 中用到
API 稳定、无认证、无分页有复杂认证、分页、重试逻辑
操作不频繁（周级别）每天多次调用
现有 CLI 工具已经很成熟（如 git）内网私有系统，没有现成 CLI

8. 关键收获

本课核心：
1. MCP server 运行在本地——stdio 或 localhost，不需要外网
2. MCP server 的网络权限 = 你机器的网络权限——能访问内网就能用
3. 内网 MCP 的最大价值 = 封装脏活（认证、分页、错误处理）
4. 判断标准不变——跨 skill 复用 + 高频 + 复杂逻辑 → MCP

9. 回到你的工作场景

你在内网做代码审查和开发。问自己：

  • 有没有反复让 AI 写相似的脚本来调内网系统？→ MCP 信号
  • 有没有因为认证/分页/API 格式问题浪费过几轮调试？→ MCP 信号
  • 你的 ide MCP 工具（getDiagnostics、executeCode）——它们就是本地运行的 MCP server。你能用它们，就能用自己写的。
