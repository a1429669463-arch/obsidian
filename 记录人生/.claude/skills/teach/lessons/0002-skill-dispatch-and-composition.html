第 2 课：Skill 调度与组合

一个 session 里有 29 个 skill，Agent 如何决定用哪个？

📅 2026-06-14 ⏱ ~20 分钟 ← 第 1 课 🎯 Mission →

1. 你的直觉是对的

你在第 1 课后提出了一个关键问题：

「在一个 agent 的任务中，多个 skills 能被同时调用吗？我的理解是因为可能有个任务需要多个 skills，才需要写清楚触发条件。」

答案是：通常一次只激活一个 skill。而这正是 Trigger Precision 存在的根本原因。

你当前的 session 里加载了 29 个 skill。每次你发一条消息，Agent 必须在 29 个候选中挑一个——或者一个都不挑。如果两个 skill 的触发条件重叠，Agent 就面临一个没有正确答案的选择题。

让我们看看这个选择过程到底怎么运作的。

2. Skill Dispatch：Agent 如何选 skill

Skill 调度（dispatch）的流程可以简化为三步：

用户消息：「帮我写一篇学习笔记」 │ ▼ ┌─────────────────────────────────┐ │ 第 1 步：扫描所有 skill 的 description │ │ │ │ study-note: 「当用户要求学习、 │ │ 了解、研究…」 │ │ feynman-test: 「当用户要求用费曼 │ │ 学习法测试…」 │ │ deep-research: 「当用户需要深度 │ │ 研究…」 │ │ …（共 29 个） │ └─────────────────────────────────┘ │ ▼ ┌─────────────────────────────────┐ │ 第 2 步：匹配 —— 谁的 description │ │ 与用户意图最吻合？ │ │ │ │ 「帮我写一篇学习笔记」 │ │ → study-note ✅ │ │ → feynman-test ❌ (没说测试) │ │ → deep-research ❌ (没说深入研究)│ └─────────────────────────────────┘ │ ▼ ┌─────────────────────────────────┐ │ 第 3 步：激活 —— 将 study-note │ │ 的 SKILL.md 注入上下文，开始执行 │ └─────────────────────────────────┘

关键点：第 2 步是纯文本匹配，没有「理解」。Agent 读你的消息，读每个 skill 的 description，然后判断哪个最相关。如果两个 description 都匹配得很好，Agent 就是在抛硬币。

3. 什么时候会出问题：触发重叠

假设你写了两个 skill，description 分别是：

Skill A 「当用户要求审查代码时使用此 skill。」

Skill B 「当用户要求检查代码质量时使用此 skill。」

用户说「帮我看看这段代码有没有问题」——两个都匹配。Agent 可能随机选一个，或者更糟：选了 A，但用户实际想要 B 的功能。

这就是 T3 检查项的意义：「和其他 skill 的触发条件无歧义重叠」。每写一个 skill 的 description，你都要问：有没有现存的 skill 也会匹配同样的用户意图？
🔍 那我是不是应该把所有功能写在一个 skill 里？

不。一个 skill 做一件事，这是好的设计（Unix 哲学）。问题不在「拆」，而在每个 skill 的 触发条件要互斥。

修复上面例子：

  • Skill A：「当用户要求审查代码的正确性和安全性时使用」
  • Skill B：「当用户要求检查代码风格和复杂度时使用」

现在「看看有没有问题」会匹配 A（正确性+安全），「这个函数太长了吧」会匹配 B（复杂度）。两个 skill 的方向不同，触发条件自然互斥。

4. 多 Skill 协作的三种模式

回到你的核心问题：多个 skill 能一起工作吗？能，但不是「同时激活」，而是通过明确的调用关系来组合。

模式 A：独立并行（Independent）

用户：「先帮我查一下 MCP 的资料，然后考考我」 │ ▼ ┌────────────────┐ │ Agent 判断：这是 │ │ 两个独立任务 │ │ │ │ 第 1 轮： │ │ 匹配 study-note │ │ → 创建笔记 │ │ │ │ 第 2 轮： │ │ 匹配 feynman-test│ │ → 开始出题 │ └────────────────┘

Agent 会分两轮处理，每轮激活一个 skill。前提是两个 skill 的 description 足够互斥，Agent 能清楚地分辨「现在该用哪个」。

模式 B：Skill 链式调用（Chaining）

Skill A (workflow) 在执行中显式调用 Skill B： study-note 的第 3 步： 「…如果用户需要验证理解， 调用 feynman-test skill…」 │ ▼ Skill("feynman-test") → 激活 feynman-test

一个 skill 可以在自己的指令里写「调用另一个 skill」。这不是两个 skill 同时激活——而是 skill A 在执行中显式启动 skill B。Skill B 完成后，控制权返回 skill A。

🛠 这在 Claude Code 中怎么写？

在 SKILL.md 的某个步骤中写：

### 第 4 步：验证用户理解
如果笔记创建完成且用户想检验理解，调用 Skill("feynman-test")。
注意：必须先等用户确认，再调用。

Agent 读到这句时，会通过 Skill 工具来激活另一个 skill。链式调用的关键是明确的条件——什么情况下调用、调用前要确认什么。

模式 C：Workflow 编排（Orchestration）

Workflow（更上层的编排机制）： export const meta = { name: 'full-research-pipeline' } phase('研究') const note = await agent('用 study-note 创建笔记', …) phase('验证') const test = await agent('用 feynman-test 出题', …) │ ▼ Workflow 按阶段依次激活不同的 skill/agent

Workflow 是比 skill 更高层的编排机制。它在代码层面定义「先调 A，再调 B，然后并行调 C 和 D」。每个阶段内部可以激活一个或多个 skill。这适合固定的多步骤流程，而非根据用户意图灵活匹配。

5. 四种模式的决策指南

场景 用什么 例子
单一任务，独立完成 一个 skill 「帮我创建一篇笔记」→ study-note
多个独立任务，先后执行 分轮激活不同 skill 「先查资料，再考考我」→ 第一轮 study-note，第二轮 feynman-test
一个 skill 内部需要另一个 skill 的能力 链式调用 study-note 完成后自动问「要不要测试理解」→ Skill("feynman-test")
固定多步骤流程，每次都要按序执行 Workflow 「完整研究管线」：搜索 → 笔记 → 验证 → 总结

6. 练习：设计互斥触发条件

场景

你要为团队写三个 skill：

  1. code-review：审查代码的正确性和安全性
  2. refactor-suggest：建议代码重构和优化
  3. debug-helper：帮助定位和修复 bug
🔍 这三者的触发条件会有重叠吗？试着想一下再点开。

有重叠风险：

  • 「这段代码有个 bug」→ debug-helper 还是 code-review？
  • 「帮我优化这个函数」→ refactor-suggest 还是 code-review？
  • 「审查一下安全性」→ 明确是 code-review，没问题

改进后的 description：

  • code-review：「当用户提交 PR、要求 review 代码变更、检查代码是否符合规范和安全标准时使用。不触发于：用户报告 bug 或要求定位问题（用 debug-helper），要求优化性能或结构（用 refactor-suggest）。」
  • refactor-suggest：「当用户要求改进已有代码的结构、可读性或性能，且代码功能正常无 bug 时使用。不触发于：代码有 bug、报错、行为异常。」
  • debug-helper：「当用户报告代码报错、行为异常、结果不符合预期时使用。不触发于：代码功能正常但需要优化（用 refactor-suggest），常规 PR review。」

注意每个 description 都写了不触发条件，指向另外两个 skill。这样 Agent 在匹配时能明确排除。

7. 关键收获

本课核心：
1. 一次一个 skill——Agent 每轮只激活一个 skill，通过 description 匹配
2. 触发重叠 = 随机选择 = 不可靠——写 description 要确保和其他 skill 互斥
3. 多 skill 协作有三种模式：分轮激活、链式调用、Workflow 编排
4. 排除条件（「不触发于」）和正面条件同样重要——它让 Agent 知道什么时候不该用你

8. 联系第 1 课

现在回头看 T-P-G 三角中的 T Trigger Precision，它的深层含义是：

Trigger Precision 的本质不是「让 skill 被正确调用」，而是「在 29 个候选中，让 Agent 能无歧义地选到你」。

你的 description 不是写给用户看的说明书——它是写给 Agent 看的选票。

9. 推荐阅读

📖 打开你的 session，输入 /skills 看看当前加载了哪些 skill。找一个你从来没用过的 skill，读它的 description——想想为什么它从来没被误触发过（或者被误触发过）。
