第 3 课：T-P-G 实战解剖

以 teach skill 为案例，逐项打分的完整分析

📅 2026-06-14 ⏱ ~20 分钟 ← 第 2 课

1. 你的观察是对的——先修正 T2

你看了「名人写的 skills」，发现他们没有显式排除条件。这让你怀疑 T2 的必要性。

你的怀疑是健康的。

回头看 T-P-G 检查清单中的 T2：

旧 T2：「是否列出了不触发的情况？」——至少 1 个排除条件

这个表述太窄了。修正如下：

新 T2：「触发条件的特异性是否足够防止误触发？用的是什么机制？」

实现触发特异性有 4 种机制，显式排除只是其中之一：

机制原理谁在用可靠度
机制 1：窄描述 description 本身足够窄和具体，自然不和别的 skill 重叠 feynman-test（「用费曼学习法测试」— 独特场景） ⭐⭐⭐
机制 2：disable-model-invocation 完全绕过 AI 匹配，只能通过显式 /command 触发 teach（本 skill！） ⭐⭐⭐⭐⭐
机制 3：领域专有词汇 用独特术语，不会被日常对话意外命中 「ZPD」「费曼」「Harness Engineering」 ⭐⭐⭐⭐
机制 4：显式排除 在 description 中写「不触发于…」 feynman-test（「普通的 XX 是什么 不触发」） ⭐⭐⭐⭐
核心原则：目标是「该来的时候来，不该来的时候别来」。至于用什么手段实现，看场景。不要把 T-P-G 当成教条——它是诊断工具，不是法律条文。

2. 案例解剖：teach SKILL.md

现在我们把这个 132 行的 skill，用 T-P-G 三角逐项打分。这是你自己的学习空间里的 skill，你每天都在看它运行。

2.1 Trigger Precision — 触发精度

看 frontmatter：

name: teach
description: Teach the user a new skill or concept, within this workspace.
disable-model-invocation: true       ← 关键！
argument-hint: "What would you like to learn about?"
T1 触发具体 ✅ 好 「Teach a new skill or concept, within this workspace」— 场景清晰，不模糊
T2 防误触发 ✅ 极好 用了机制 2：disable-model-invocation: true — AI 永远不会自动匹配这个 skill，只有用户显式输入 /teach 才触发。这比任何排除条件都强。
T3 无歧义重叠 ✅ 好 「teach」这个名字没有其他 skill 用。如果有个 skill 也叫类似名字（比如「tutor」「instruct」），就会有重叠风险。
T4 变体覆盖 ⚠️ 略弱 用户不说 /teach 而是说「教我 XX」「我想学 YY」时不会触发——但这是故意的，因为 disable-model-invocation 本身就是「只有显式调用才触发」的设计选择。
🔍 disable-model-invocation: true 是什么意思？

这是 Claude Code 的 skill frontmatter 字段。默认情况下，AI 可以根据 description 自行判断是否调用一个 skill。加上这个字段后，AI 永远不会主动调用这个 skill——它只能通过用户显式输入 /teach 来触发。

这意味着 teach skill 的「触发判断」完全由用户（人）来做，而非 AI。这是 最强的 Trigger Precision——消除了所有 AI 误判的可能。

代价：用户如果不主动输入 /teach，这个 skill 永远不会被触发，即使上下文完全适合用它。

2.2 Procedure Clarity — 流程清晰度

teach skill 的结构不是线性的「第 1 步 → 第 2 步」，而是一组原则和规范。这是有意为之的设计选择——教学不是流水线，不能机械执行。

P1 原子动作 ⚠️ 模糊 没有「第 1 步 / 第 2 步」的线性流程。Agent 需要自行判断该看哪个 section。这不是缺点——教学本身就非线性——但会导致 Agent 行为不够一致。
P2 动词可执行 ⚠️ 混合 有些动词很具体（「Read their learning-records」「Create a lesson」），有些很模糊（「should be designed」「should be used to ground」）。
P3 输入输出 ⚠️ 隐含 lesson 的格式（HTML 结构）、learning record 的格式有详细规定，但没有说「读到 MISSION.md 后输出什么」。
P4 决策分支 ⚠️ 依赖判断 「If the user is unclear about the mission, your first job should be to question the user...」— 这是一个分支，但判断「unclear」完全依赖 Agent 的主观判断。
P5 引用精确 ✅ 好 引用都用了完整的相对路径：[MISSION-FORMAT.md](./MISSION-FORMAT.md)、[LEARNING-RECORD-FORMAT.md](./LEARNING-RECORD-FORMAT.md)。
Procedure 的诊断不是「好/坏」的二元判断。 teach skill 的 Procedure Clarity 看起来「弱」，但这是有意为之：教学需要灵活性，过度约束反而会让课程变得机械。关键在于你知道这个 trade-off 并接受它。

2.3 Guardrails — 护栏完整度

这是 teach skill 的强项。虽然 Procedure 比较松散，但护栏很多：

# 从 skill 原文中提取的护栏（非连续，仅为示例）

"Never trust your parametric knowledge."
"Confirm with the user before changing the mission."
"Push back on vagueness."
"A bad mission is worse than no mission."
"Keep it short."
"Respect it." (指用户不加入社区的偏好)
"Prune ruthlessly."
"If the user cannot articulate why, interview them before writing anything."
G1 绝对禁止 ✅ 强 「Never trust your parametric knowledge」— 极强的硬约束，明确告知 Agent 不能用训练数据凑答案。
G2 信息不足 ✅ 好 「If the user cannot articulate why, interview them before writing anything」— 信息不足时向用户获取，而非猜测。
G3 失败恢复 ⚠️ 缺失 如果 lesson HTML 写坏了怎么办？如果格式文件读取失败怎么办？没有明确的恢复策略。
G4 输出格式 ✅ 强 每种文件的格式都有独立的 FORMAT.md 参考文件，结构规定得很细。
G5 确认节点 ✅ 好 「Confirm with the user before changing the mission」— 不可逆操作前需要用户确认。

3. 综合诊断

Trigger ★★★★★ disable-model-invocation + 窄描述，几乎不可能误触发
Procedure ★★★☆☆ 有意保持灵活，但代价是 Agent 行为可能不够一致
Guardrails ★★★★☆ 约束丰富，但缺少失败恢复策略

teach skill 的设计哲学是：用极强 Trigger（防误入）+ 丰富 Guardrails（防乱做）来补偿宽松的 Procedure。这是一个合理的工程设计 trade-off——当任务本质上不适合机械流程时，你可以选择「收紧两端，放松中间」。

这就是 T-P-G 框架的真正用法：不是追求三角都满分，而是理解每个 skill 的 trade-off，并确保弱的那一角有其他两个兜底。

4. 对比：两种设计哲学

study-note（你的 skill） teach（本 skill）
T Trigger 基于 description 匹配，有排除条件 disable-model-invocation，只靠 /teach
P Procedure 线性 6 步流程，每步有明确动作 非线性的原则和规范集合
G Guardrails 检查清单 + 验证步骤 丰富的禁令和建议
适合场景 确定性任务（创建笔记有模板） 不确定性任务（教学需要灵活）
设计哲学 弱 T + 强 P + 强 G
「我知道你会被正确触发，但我用流程和护栏确保你做对」		 强 T + 弱 P + 强 G
「我限制进入条件，之后给你自由度，但用护栏兜底」

5. 练习：用修正后的 T-P-G 评估你自己的 skill

✏️ 练习 1：重评 study-note 的 Trigger

用新 T2 标准（「特异性是否足够？用什么机制？」）重新评估 study-note：

  1. 它用的是机制 4（显式排除）吗？——没有显式排除条件
  2. 它用的是机制 1（窄描述）吗？——「学习」「了解」「研究」「创建笔记」覆盖面很广，不算窄
  3. 它和 feynman-test 有重叠吗？——有。用户说「帮我学习 X」应该触发 study-note，但如果 X 是已有笔记，feynman-test 也可能被触发

改进方向：考虑加入显式排除，如「不触发于：用户要求测试已有知识的理解程度（用 feynman-test）」。

✏️ 练习 2：诊断 procedure 的 trade-off

teach skill 的 Procedure 偏弱，但这是有意的。想一个问题：

如果强行把 teach skill 写成线性流程（第 1 步→第 2 步→…），会出什么问题？

可能的答案：

  • 第 1 步永远是「检查 MISSION.md」——但如果 MISSION.md 不存在呢？（已经写了分支处理）
  • 课程创建在不同阶段取决于不同情况，线性流程会让简单场景变复杂
  • 教学中的「判断 ZPD」本质上需要 Agent 的灵活性，机械流程做不好

结论：有些 skill 的任务本质就是非线性的——不是设计缺陷，是领域特征。

6. 关键收获

本课核心：
1. T-P-G 是诊断工具，不是评分标准——不需要三角满分，需要知道哪里弱、怎么补偿
2. 排除条件只是 4 种 Trigger Precision 机制之一——disable-model-invocation 更强
3. Procedure 弱不一定是 bug——如果任务本质非线性，用 Trigger + Guardrails 补偿
4. 看别人的 skill 时，不要只找「有没有排除条件」，要看「它是怎么解决误触发问题的」
