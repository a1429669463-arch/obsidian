第 6 课：MCP 实战

你已经接入了 2 个 MCP 工具——现在要学会「什么时候该用 MCP 而不是 CLI」

📅 2026-06-14 ⏱ ~20 分钟 ← 第 5 课

1. 先看一个事实

输入 /context，看 MCP tools 那一栏：

MCP tools · /mcp
└ 2 tools · 0 tokens

你有 2 个 MCP 工具正在运行：mcp__ide__executeCode 和 mcp__ide__getDiagnostics。你已经在用 MCP 了，只是当它是「IDE 自带功能」而非「MCP 工具」。

第一件事：MCP 不是什么遥远的技术——它就是你当前 session 里那两个 mcp__ide__* 工具。就像你不会觉得「我在用 HTTP」——你只是在用浏览器。MCP 是传输层，工具才是你感受到的东西。

2. 你现在的做法 vs MCP 的做法

你说「平时都是让 AI 写 CLI 工具」。假设你要查当前目录下所有 .md 文件的行数——

CLI 路径（你现在）MCP 路径
怎么做 AI 写一段 PS 命令 → 调用 PowerShell 执行 → 解析输出 AI 调用 mcp__filesystem__count_lines
AI 需要知道什么 PowerShell 语法、文件路径规则、输出格式 工具名 + 参数：{pattern: "*.md"}
出错时 PS 语法错误、路径转义问题、编码问题 工具返回结构化错误信息
跨平台 换 Linux 要重写 bash 版本 同一工具、同一接口

CLI 路径的本质：用通用工具（shell）做特定的事，AI 需要自己翻译「意图 → 命令」。这在简单场景下没问题，但翻译过程本身就是不确定性来源。

MCP 路径的本质：把特定操作封装成结构化的工具接口，AI 不需要知道底层怎么实现。

3. 决策框架：什么时候该用 MCP？

每当你需要给 AI 一个「新能力」时，走这个决策树：

Q1: 这个操作 AI 能否用现有工具完成（shell、文件读写、WebSearch）？

→ 能，且简单 不需要新东西，直接用

→ 能，但需要复杂脚本 看 Q2

Q2: 这个操作是否在多个 skill 中重复出现？

→ 是 MCP — 封装一次，多 skill 复用

→ 否，只在一个 skill 中用 看 Q3

Q3: 出错时，AI 能自己诊断和修复吗？

→ 能（简单脚本，易调试） CLI 就够

→ 不能（需要专门知识、权限、状态管理） MCP

🔍 具体例子：什么时候选 MCP？
场景决策理由
查文件行数 CLI ✅ 一个 PS 命令搞定，不会出错
在多个 skill 中需要查询 Jira issue MCP ✅ 复用 + Jira API 有认证和分页逻辑，CLI 脚本容易出错
查当前 IDE 的诊断错误 MCP ✅ 你已经在用了——mcp__ide__getDiagnostics。它不需要 AI 知道 VS Code 的内部 API。
格式化一个 JSON 文件 CLI ✅ 一行 ConvertFrom-Json，不需要专门工具
操作数据库（查/写/迁移） MCP ✅ 连接管理、SQL 注入防护、事务——CLI 脚本不可靠

4. MCP 的隐藏成本：上下文 token

你 MCP 笔记里已经写了：「接入过多 MCP 工具时，元信息会占用上下文」。这是对的，但还不够具体。

每个 MCP 工具的描述、参数名、参数类型、参数描述——全部占上下文。看你的 ide 工具：

mcp__ide__executeCode    — 0 tokens  ← 因为还没被调用过
mcp__ide__getDiagnostics — 0 tokens

0 token 是因为这些工具的定义很轻量。但如果你接入一个有 20 个方法的数据库 MCP server，每个方法有 5 个参数——那就是几百个 token，永久占用上下文。这就是你笔记里提到的问题。

MCP 的上下文成本公式：
固定成本 = 所有工具的 name + description + parameters schema
变动成本 = 每次调用的参数 + 返回值

关键决策：固定成本值得付吗？如果这个 MCP 工具每月只用一次——不值得。如果每天用 10 次——值得。

5. MCP + Skill：它们怎么配合？

这是你之前可能没想过的一个组合：

SkillMCP 工具
作用告诉 AI 怎么做（流程 + 约束）给 AI 做事的工具（能力）
类比标准操作流程（SOP）工具箱里的工具
谁管谁Skill 的 Procedure 中调用 MCP 工具MCP 工具被 Skill 命令式调用

好 skill = 在正确的步骤调用正确的 MCP 工具。

# 一个 skill 步骤中调用 MCP 的实例（伪代码）

### 第 3 步：检查代码质量
3a. 调用 mcp__ide__getDiagnostics(uri="{当前文件路径}")
3b. 如果有 error 级别诊断 → 先修复 error，再继续
3c. 如果只有 warning → 记录到审查意见中，继续

Skill 说「什么时候用」，MCP 说「怎么执行」。这是 Skill + MCP 的标准配合模式。

6. 你自己写一个 MCP 工具的场景

你说「平时让 AI 写 CLI 工具」。下面是你可能会遇到的第一个「应该用 MCP」的信号：

信号：你发现自己在多个 skill 里让 AI 写了类似但不完全相同的 PS 脚本，而且偶尔会因为脚本写错而浪费几轮对话来调试。

这意味着：你应该把这个操作封装成一个 MCP 工具。封装一次，所有 skill 直接调用。
🛠 MCP 工具怎么写？（概要）

一个 MCP 工具就是一段代码 + 一个描述文件。以 Python 为例：

  1. 写一个函数，定义输入参数和返回值
  2. 用 MCP SDK 包装成 tool
  3. 在 Claude Code 的 .claude/mcp.json 中注册

但你现在不需要自己写——先用好已有的 MCP 工具，感受它们的价值。当「CLI 脚本反复出错」这个信号出现时，再考虑自己写。

7. 练习：有意识地用现有的 MCP 工具

✏️ 任务

  1. 打开一个代码文件，故意写一个错误（比如未定义的变量）
  2. 对我说：「用 MCP 工具检查当前文件的诊断信息」
  3. 观察 mcp__ide__getDiagnostics 怎么被调用、返回什么
  4. 然后再对我说：「根据诊断结果，用 MCP 工具执行一段代码来验证」
  5. 对比：如果不用 MCP，AI 会怎么做？（写 PS 脚本猜测错误）

这就是 MCP 实战——不是搭建服务器，而是有意识地使用已有的 MCP 工具。

8. 关键收获

本课核心：
1. 你已经在用 MCP——ide 的 2 个工具就是 MCP
2. CLI vs MCP 决策树：跨 skill 复用 → MCP；一次性操作 → CLI
3. MCP 的固定成本是上下文 token——只为高频操作买单
4. Skill 管流程，MCP 管能力——好的 skill 在正确的步骤调用正确的 MCP 工具
5. 封装 MCP 的信号：多个 skill 中让 AI 写类似脚本，且脚本反复出错
