第 9 课：缓存命中率

你 Context Engineering 工作的财务回报——每一 token 的缓存命中都在省钱

📅 2026-06-14 ⏱ ~25 分钟 ← 第 8 课

1. 从一组数字开始

基础价缓存命中
输入 token100%~10%
缓存写入—125%（5min TTL）/ 200%（1h TTL）
一句话：缓存命中的 token 只需支付原价的十分之一。你第 4 课学的 Context Engineering 决定哪些内容进入缓存、哪些破坏缓存。结构好 = 省钱 + 加速。

这不是小优化。Anthropic 团队像监控服务器 uptime 一样监控缓存命中率——掉几个百分点就会触发 SEV（严重事件）。一位工程师一周靠缓存优化省了 3 亿 token。

2. 缓存如何工作：前缀匹配

每次你发消息，API 不会「记住」之前的对话。Claude Code 把完整的上下文——系统提示、项目上下文、全部历史消息——重新发送。新增内容追加在末尾。

缓存的机制是前缀匹配：API 比对请求的开头部分与之前处理过的内容。如果前 N 个 token 完全一致 → 命中缓存，只需处理新增部分。

关键推论：前缀任何位置的改变，都会使该位置之后的所有内容缓存失效。缓存不是按文件、按段落匹配的——是从头开始逐 token 比对。

3. 四层结构：静态在前，动态在后

Claude Code 将每次请求排列为四层，越靠前的层越稳定：

① 系统提示 + 工具定义 ← 最稳定（Claude Code 升级或 MCP 工具集变更时才变）
② 项目上下文（CLAUDE.md、memory、rules） ← 会话启动或 /compact 时重新加载
③ 会话上下文 ← 逐轮追加
④ 对话消息（你的消息 + AI 回复 + 工具结果） ← 每轮都在变

第 ① 层变了 → 全部缓存失效。第 ④ 层变了 → 前三层依然命中。这就是为什么 「静态在前，动态在后」是缓存优化的铁律。

4. 缓存杀手：这 8 个操作会让缓存全部重建

操作为什么破坏缓存可避免？
🔄 切换模型 每个模型有独立缓存。内容相同，换模型 = 全量重算 ✅ 会话开始时选定模型
⚡ 改变 effort level effort level 是缓存 key 的一部分 ✅ 会话开始时设定
🔌 MCP server 连接/断开 工具定义在系统提示层，变化 → 前缀全变（defer_loading 模式下除外） ⚠️ 部分可控（见第 6 节）
📦 /compact 压缩 消息历史被替换为摘要，前缀不匹配 ⚠️ 在任务间隙手动触发，而非等自动触发
⬆️ Claude Code 升级 系统提示或工具定义更新 ✅ 升级不发生在会话中（启动时生效）
🚫 deny 整个工具 deny 规则从上下文中移除工具定义 → 前缀变化 ✅ 用限定 deny（如 Bash(rm *)），不 den 整个工具
🔧 启用/禁用插件 若插件提供 MCP server，同 MCP 规则 ⚠️ Skills/commands/hooks 类插件不影响缓存
⚡ 开启 fast mode 添加了请求头 → 缓存 key 变化 ✅ 会话开始时开启
Opus Plan 模式特别提醒：如果你配置了 opusplan——进入 plan 模式用 Opus，执行时用 Sonnet——每次模式切换就是一次模型切换，缓存重建。这不是 bug，是设计选择——但你要知道它有成本。

5. 缓存安全：这些操作不破坏缓存

操作为什么安全
✏️ 编辑文件文件内容只在读取时进入上下文，编辑不回溯修改已有的读取记录
📝 编辑 CLAUDE.md会话中不重新加载——读到的是会话启动时的版本
🎨 改输出风格会话启动时读入系统提示，会话中不重新读取
🔓 切换权限模式不改变系统提示或工具定义（plan mode + opusplan 除外）
📥 调用 Skill / 命令Skill 指令以用户消息形式追加在末尾，前缀不变
⏪ /rewind 回退截断到更早的轮次，该轮次的前缀仍在缓存中（只要被持续读取过）
🤖 启动子代理子代理有独立的缓存，父代理的缓存不受影响
Skill 是缓存友好的：Skill 指令以用户消息的形式追加，不修改前缀。这意味着你在 skill 里写再多指令，也不会破坏已有的缓存——Skill 的设计天然保护缓存。

6. Skill 与缓存：你可以控制什么

回到你的 Mission——设计更好的 Skill。Skill 本身就缓存安全，但你还能做得更多：

6.1 CLAUDE.md 要精不要多

CLAUDE.md 在系统提示之后的第 ② 层，跨会话可能共享缓存。但它每次会话启动都被读取，是前缀的一部分。

放什么不放什么
构建/测试命令、架构边界、编码约定背景叙述、完整 API 文档、模糊的原则
NEVER/ALWAYS 硬约束「合适的」「清晰的」等模糊形容词
Compact 存活指令每个文件的详细说明
2.5K token 以内超过 3K token 的 CLAUDE.md

这恰好是你第 4 课学会的信息密度公式的另一个应用：短 CLAUDE.md = 低缓存写入成本 + 高跨会话复用率。

6.2 MCP 工具的 defer_loading

MCP 工具定义在系统提示层，是缓存失效的最大隐藏杀手。默认情况下，Claude Code 对支持的模型使用 defer_loading——只发轻量 stub（工具名 + defer_loading: true），模型选中后才加载完整 schema。

对你的意义：你写内网 MCP server（第 7 课）时，不需要为缓存做额外的事——defer_loading 已自动保护。但如果你标记了 alwaysLoad: true，该 server 的工具定义会进入前缀，server 重连就会破坏缓存。

6.3 不要在 Skill 描述里放动态内容

Skill 的描述（SKILL.md 的 frontmatter description）会在会话启动时加载为系统提示的一部分（在第 ① 层之后）。虽然 Skill 调用本身在消息层追加，但 Skill 元信息列表是静态前缀的一部分。

如果你用脚本动态生成 SKILL.md 的 description 且内容每次不同 → 每次会话启动前缀都不同 → 跨会话无法复用缓存。

7. TTL：缓存活多久

场景TTL说明
Claude 订阅1 小时自动启用，不额外收费
API Key5 分钟默认。设 ENABLE_PROMPT_CACHING_1H=1 可升到 1 小时
子代理总是 5 分钟即使主会话有 1 小时 TTL
配额用完后降为 5 分钟用量按 token 计费后自动降级

每次缓存命中会重置计时器。你持续工作时，缓存一直存活。离开超过 TTL → 下次请求全量重算。

8. 监控：怎么看缓存有没有在工作

你的 statusline 已经配置好了。每次 API 响应中有两个关键字段：

字段含义
cache_creation_input_tokens本轮写入缓存的 token（按写入价计费）
cache_read_input_tokens本轮从缓存读取的 token（按 ~10% 价计费）

读/写比高 → 缓存工作良好。写入持续很高 → 前缀在频繁变化，排查第 4 节列表。

9. 回到你的工作场景

你在设计 Skill 和工作流时，缓存优化不是独立步骤——它是你已有的 Context Engineering（第 4 课）和 Skill 开发闭环（第 5 课）的自然延伸：

你已有的原则缓存维度的翻译

五步闭环的「观察」阶段加入缓存指标观察（cache_read / cache_creation 比例）

10. 你的实战检查清单

每次设计/审查 Skill 或 CLAUDE.md 时问自己：

□ 最稳定的内容放在最前面了吗？
□ CLAUDE.md 有没有可以删掉的背景叙述？
□ 工具集在会话中会变吗？（变了 = 缓存全毁）
□ 有没有动态内容（时间戳、随机 ID）出现在前缀层？
□ 大文件是放在 Projects 里还是直接贴进聊天？（后者贵 10 倍）
□ 会话间隙超过 TTL 有没有做 handoff？（见下文）

Handoff 模式：任务切换时保护投资

当你需要切换任务但不想丢失进度：

1. 让 Claude 总结当前进度 → 生成 handoff 摘要
2. /clear 清空会话
3. 粘贴 handoff 摘要，开始新任务
4. 新会话的缓存从头开始，但旧会话的 token 不会继续膨胀

11. 关键收获

本课核心：
1. 缓存 = 前缀匹配——前缀任何位置改变，之后全部失效
2. 静态在前，动态在后——这是所有缓存优化的根基
3. 8 个缓存杀手——切换模型、改 effort、MCP 变动、compact、升级、deny 工具、插件 MCP、fast mode
4. Skill 天然缓存安全——指令以用户消息追加，不修改前缀
5. CLAUDE.md 精短 = 省钱——2.5K token 以内，每多 1K 就是每次会话启动的额外缓存写入成本
6. 缓存命中率 ≈ 你的上下文结构质量指标——高命中 = 结构好，低命中 = 前缀在频繁变化

12. 检验理解

Q1：你在会话中编辑了 CLAUDE.md，加了一条新规则。这条规则会立即生效吗？会破坏缓存吗？

不会立即生效，也不会破坏缓存。

CLAUDE.md 在会话启动时一次性读入内存。编辑文件不回溯修改内存中已加载的版本。新规则在下一次 /clear、/compact 或重启后生效。这是故意设计——如果每次编辑 CLAUDE.md 都重新加载，前缀就会变，缓存就毁了。

Q2：你的 study-note skill 被调用时，会破坏当前会话的缓存吗？为什么？

不会。

Skill 调用时，其指令以用户消息的形式追加在对话末尾。消息在缓存四层结构的最外层（第 ④ 层），前面的系统提示、项目上下文、历史消息的前缀完全不变。缓存只对新增的 skill 指令 token 收费，前面全部命中。

Q3：你用 /model 从 Sonnet 切到 Opus 处理一个难题。这个切换有隐藏成本吗？

有。下一次请求缓存全部重建。

每个模型有独立的缓存空间。即使请求内容完全一样，Opus 无法读取 Sonnet 的缓存。切换后的第一轮要全量重算整段对话历史——这轮会比平时慢得多、贵得多。更好的做法：在会话开始时就选定模型，或用子代理（子代理可以用不同模型，但不影响父会话缓存）。
