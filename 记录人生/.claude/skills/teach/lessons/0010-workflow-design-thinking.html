第 10 课：工作流设计思想

从「会用工具」到「会设计」——面对空白需求时，如何思考出合理的工作流

📅 2026-06-17 ⏱ ~25 分钟 ← 第 9 课 🎯 Mission →

1. 你已经有了所有工具。现在缺什么？

回顾前 9 课，你掌握了：

  • T-P-G 三角：诊断任何 skill 好坏的框架
  • 调度与组合：独立并行 / 链式调用 / Workflow 编排三种模式
  • Context Engineering：信息密度公式、预算测试、渐进式披露
  • 五步闭环：设计 → 测试 → 观察 → 诊断 → 修复
  • MCP + Hooks + 缓存：何时用哪个、怎么配、怎么优化

这些都是执行层的工具。但是——

面对一个全新的自动化需求，你的第一反应是什么？

如果你先想「我用 T-P-G 来检查」「我用五步闭环来迭代」——那你已经在用工具了。但在这之前，有一个更根本的问题：

这个需求应该被拆成什么样的工作流？为什么拆成这样而不是那样？

这就是设计思想——在拿起工具之前，先建立问题的形状。

2. 第一性原理：工作流 = 约束的序列

回忆第 1 课的核心洞察：好的 skill 是一个约束引擎，每一步都在收窄 AI 的选择空间。

把它提升一层：

工作流设计的本质 = 把一个复杂问题分解成一系列子问题，每个子问题小到 AI 只有一种正确的做法。

不是「AI 应该怎么做」——那是给指令。
而是「把问题切成什么形状，AI 才不会做错」——那是做设计。

这意味着：你的主要工作不是写 prompt，是设计问题的分解结构。分解得好，每一段的 prompt 可以很简单。分解得不好，prompt 写再多也兜不住。

3. 思维工具一：层级任务分解（HTA）

HTA（Hierarchical Task Analysis）是人因工程学最经典的任务分解方法。它问一个递归的问题：

「要完成这一步，需要先完成哪些子步骤？」
一级一级往下拆，直到每个子步骤都简单到不可再分——也就是 AI 能无歧义执行的动作。

以你的 study-note skill 为例，用 HTA 的视角看它的设计：

0. 创建一篇学习笔记 │ ├── 1. 搜索已有笔记（防重复） │ ├── 1a. 从用户问题提取关键词 │ ├── 1b. Grep 搜索知识库 │ └── 1c. 判断是否已存在 → 存在则告知用户，不存在则继续 │ ├── 2. 网络搜索获取知识 │ ├── 2a. WebSearch 搜索（1-2 次） │ ├── 2b. WebFetch 获取关键页面详情 │ └── 2c. 判断信息是否足够 → 不够则补充搜索 │ ├── 3. 规划文件结构 │ ├── 3a. 判断应该是一个文件还是多个文件 │ ├── 3b. 列出文件清单 │ └── 3c. 等待用户确认 │ ├── 4. 按规范写入 │ ├── 4a. 写 frontmatter（date + tags） │ ├── 4b. 写一句话定义 │ ├── 4c. 写正文 │ ├── 4d. 写参考文献 │ └── 4e. 写相关笔记 [[wikilink]] │ └── 5. 最终检查 ├── 5a. 对照 note-rules.md 逐项检查 └── 5b. 报告结果

注意几个设计决策：

  • 第 1 步和第 2 步有先后——先查本地再搜网络（省成本、防重复）。这是 Pipeline 模式。
  • 第 4a-4e 是顺序固定——因为每项内容不同，不需要并行。
  • 第 3c 插入了人——不可逆操作（写入多个文件）前必须确认。这是 Human-in-the-Loop。

这些决策不是「按模板填的」——它们是基于问题本质做的设计选择。

4. 思维工具二：六种工作流设计模式

HTA 帮你拆问题。但拆完之后，子步骤之间怎么组织？这里有六种可复用的模式。它们是 Anthropic「Building Effective Agents」中总结的基础构件，加上传统工作流引擎中最核心的补偿模式。

模式 1：Pipeline（链式管道）顺序

每一步的产出 = 下一步的输入。有严格的先后顺序。

[搜索] → [阅读] → [分析] → [写入] 每个 gate 可以检查上一步的输出质量，不达标就重做

何时用：任务天然有先后依赖。上一步的结果决定下一步做什么。

你的 study-note 就是 Pipeline：搜索 → 规划 → 写入 → 检查。不能跳过搜索直接写。

模式 2：Routing（路由分流）分支

根据输入特征，分流到不同的处理路径。

用户请求 │ ├── 「学习 XX」 → study-note ├── 「考考我」 → feynman-test └── 「深入研究 XX」 → deep-research

何时用：同一入口，不同意图，需要不同处理。分类必须准确——如果分类器经常搞错，Routing 反而增加错误。

在 Skill 内部也能用：比如 study-note 判断「是一个文件还是多个文件」→ 走不同写入路径。

模式 3：Parallelization / Fan-out（并行扇出）并行

多个独立子任务同时进行，结果汇总。

┌→ 查资料 A ──┐ 一个需求 ──┼→ 查资料 B ──┼→ 汇总 → 写入 └→ 查资料 C ──┘

何时用：子任务之间没有依赖关系，各自独立。

两种变体：(1) Sectioning — 不同子任务各做各的；(2) Voting — 同一个任务做多次，取多数意见。

第 2 课学到的独立并行模式就是 Fan-out 的特例——Agent 分两轮激活不同 skill。

模式 4：Orchestrator-Workers（编排-工人）动态

一个中央编排者动态分解任务，分配给多个工人，最后合成结果。

Orchestrator: 「用户要学习 MCP + Hooks 的关系」 │ ├→ Worker 1: 研究 MCP 的概念和用途 ├→ Worker 2: 研究 Hooks 的概念和用途 └→ Worker 3: 研究两者的配合模式 │ Orchestrator: 合成三份结果 → 检查一致性 → 写成笔记

何时用：任务复杂到无法事先确定需要多少子任务，需要动态分解。

与 Fan-out 的区别：Fan-out 的子任务是事先确定的；Orchestrator-Workers 的子任务是运行时动态决定的。

模式 5：Evaluator-Optimizer（评估-优化循环）迭代

一个生成，一个评估。评估不通过就重新生成，直到通过。

生成 ──→ 评估 ──→ 不通过？→ 带着反馈回到生成 │ 通过？→ 输出

何时用：有明确的、可验证的质量标准。评估可以自动化时效果最好。

你已经在用了：study-note 的第 5 步「对照 checklist 逐项检查」就是一个手动版的 Evaluator-Optimizer。如果能把 checklist 变成自动检查（比如检查 frontmatter 格式、检查是否有参考文献），就是完全自动化。

模式 6：Human-in-the-Loop（人机回路）确认

关键节点插入人工确认，确认后才继续。

AI 规划 → [等待用户确认] → AI 执行 → [等待用户确认] → 继续

何时用：后果不可逆（写入文件、修改配置、花费金钱）、AI 判断置信度低、或需要人的偏好做决策。

你不是在「加入确认步骤」——你是在设计信任边界。哪些决定 AI 可以做？哪些必须人来做？这个边界的划分，是工作流设计中最核心的判断之一。

5. 决策框架：你面对一个新需求时，先问什么？

六种模式不是互斥的——一个完整的 skill 通常组合使用多种模式。但你需要一个启动思考的顺序：

1 这个任务有天然的顺序依赖吗？
有 → Pipeline。子步骤的产出决定下一步做什么。

2 有可以同时做的独立子任务吗？
有 → Fan-out。但要确保子任务之间真的没有隐性依赖。

3 任务复杂到无法事先规划所有步骤吗？
是 → Orchestrator-Workers。让 AI 动态分解。

4 有客观的质量标准可以反复检查吗？
有 → Evaluator-Optimizer。生成-评估循环。

5 哪些步骤的后果不可逆？
每个不可逆步骤前 → Human-in-the-Loop。

6 输入有不同类别需要不同处理吗？
有 → Routing。但要确保分类本身可靠。

这个顺序不是教条——它是一个启动思维的习惯。用得多了，你会自然地在脑中跑这个检查清单，甚至开始凭直觉判断。

6. 设计原则：跨模式通用的判断力

以下原则不绑定任何模式，但在每种模式中都适用。它们是你做设计决策时的「宪法」。

原则含义违反时的症状
一步一动作 每个步骤只做一件事，有明确的输入和输出 AI 在某一步「自由发挥」，结果不可预测
原子性 一步要么完整成功，要么完整失败。不存在「做了一半」 文件写了一半停了，状态不一致
显式 I/O 每一步的输入来源和输出去向明确标注。上一步的输出 = 下一步的输入 中间步骤的产物丢失，后续步骤重新推断
幂等性 同一步执行多次，效果和执行一次一样 重试时创建了重复文件 / 重复操作
Fail-safe 默认 出错了默认采取最安全的做法（停下来问用户），而非最省事的做法（猜一个继续） AI 在不确定时猜了一个答案，猜错了
不可见步骤 人自动跳过但 AI 不会的步骤，必须显式写出来 AI 跳过了一个「常识性」的检查步骤
🔍 「不可见步骤」是什么意思？举个例子

人写笔记时，看到一篇好文章会自然地判断「这个值不值得记」。这个判断对人来说太自然了，以至于你不会把它写进流程。

但 AI 不会做这个判断。如果你不写「第 0 步：判断用户的问题是否值得创建一篇独立笔记。如果只是一个简单事实（如『巴黎是法国首都』），直接回答，不要创建笔记」——AI 会为任何问题创建笔记。

识别不可见步骤的方法：自己手动执行一遍任务，录下每一步你实际做了什么。然后问：有哪些操作你做了但没意识到？把这些写成显式步骤。

7. 把一切串起来：工作流设计的思维流程

面对一个新需求：「帮我设计一个能做 X 的 skill」 第 1 层：分解（HTA） 「X 这个任务，从开始到结束，要经历哪几个阶段？」 → 画出 3-7 个顶层步骤，确保覆盖了完整的生命周期 第 2 层：选模式（6 Patterns） 「每一步之间是什么关系？顺序？并行？分支？循环？」 → 为每对相邻步骤选组织模式 第 3 层：加护栏（Guardrails） 「每一步最蠢的失败方式是什么？拦住了吗？」 → 硬约束（绝对不能做的事）+ 兜底（做不了时怎么办） 第 4 层：定边界（Trust Boundary） 「哪些决定 AI 自己做？哪些必须问人？」 → 不可逆操作前 = Human-in-the-Loop 第 5 层：补不可见步骤 「我自己做这件事时，做了哪些没意识到的判断？」 → 把隐性知识写成显式步骤

注意：第 1 层和第 2 层决定了 80% 的设计质量。如果分解错了，后面加再多护栏也只是在错误的结构上打补丁。

8. 动手练习：为一个新需求设计工作流

✏️ 练习：设计一个「代码审查 Skill」的工作流

场景：你的团队需要一个 skill，当用户提交 PR 或说「帮我 review 这段代码」时触发。要求：

  • 检查代码的正确性（逻辑错误、边界条件）
  • 检查安全性（注入、权限、敏感信息）
  • 检查可维护性（命名、结构、复杂度）
  • 输出结构化的 review 意见，按严重程度分级

用四层思维流程来设计：

  1. 分解：这个任务有哪些顶层步骤？写出 3-6 步。
  2. 选模式：正确性、安全性、可维护性三者——是顺序检查还是并行检查？为什么？
  3. 加护栏：如果代码太长（超过上下文窗口），怎么办？如果用户给的既不是 PR 也不是代码片段，怎么办？
  4. 定边界：AI 发现的问题是否直接写入 PR comment？还是先列出来等用户确认？

💡 不要急着翻答案。在纸上画出你的工作流结构，然后带着你的设计来找我讨论。我会帮你分析你的设计选择。

🔍 参考答案（点开前先自己设计）

第 1 层：分解

  1. 获取代码（读取 PR diff 或用户粘贴的代码）
  2. 判断代码规模 → 如果太大，要求用户缩小范围
  3. 正确性检查：逻辑错误、边界条件、空值处理
  4. 安全性检查：注入风险、权限问题、敏感信息泄露
  5. 可维护性检查：命名、结构、复杂度、重复代码
  6. 汇总：合并三项检查结果，按严重程度分级，生成结构化输出

第 2 层：选模式

步骤 3、4、5 应该并行（Fan-out），而非顺序。原因：正确性、安全性、可维护性是三个独立的维度，彼此没有依赖。如果顺序做，不仅慢，而且 AI 在前一个维度的分析可能影响后一个维度（上下文污染）。并行做，每个维度有独立的关注点，结果更干净。

第 3 层：加护栏

  • 代码超过 500 行 → 要求用户指定范围，不自动截断
  • 输入不是代码 → 告知用户这不适合 code review
  • 每一项发现必须附带行号和代码片段，不可模糊描述
  • 不确定的发现标注「低置信度」，不假装确定

第 4 层：定边界

AI 列出发现 + 分级 → 用户确认 → 用户决定哪些要改。AI 不直接修改代码（不可逆），除非用户明确说「全部按建议修改」。

你的设计和这个答案有什么不同？不同不一定是错——可能你有更好的理由。

9. 关键收获

本课核心：
1. 工作流设计 = 问题分解——把复杂问题切成 AI 不会做错的子问题
2. HTA 是分解工具——递归地问「完成这一步需要哪些子步骤」，拆到不可再分
3. 六种模式是组织工具——Pipeline / Routing / Fan-out / Orchestrator / Evaluator-Optimizer / Human-in-the-Loop
4. 四层思维流程——分解 → 选模式 → 加护栏 → 定边界 → 补不可见步骤
5. 分解决定 80% 的设计质量——分解对了，prompt 可以很简单。分解错了，护栏也救不回来。
