## 关键原则  
  
1. 不要给 Agent 一本大说明书，要给它一张地图。  
```
也就是说，不要把所有规则、规格、经验一次性塞进上下文，而是设计一个入口，让 Agent 根据任务类型逐步读取相关资料。  
```
  
2. Agent 看不到的信息，对它来说就不存在。因此，文档要版本化，最好放进 repo，成为记录系统。  
```
文档版本化 = 文档也交给 Git 管理  
记录系统 = 项目中最可信的信息来源，用来记录业务规则、设计判断、客户要求和自身经验  
放进 repo = 让 AI、团队成员、未来的自己都能稳定找到，并且可以反复使用  
```
3. 规则不要只写在文档里，能机械化就机械化。  
```
弱规则：请注意代码结构  
强规则：如果违反依赖方向，CI 直接失败
也就是说，文档可以告诉 Agent 应该怎么做，但测试、lint、CI、脚本可以直接判断它有没有做到。
```  
4. 当 Agent 做不好时，不只是重试，而是分析它缺少什么。
```
可能缺少的是：  
 信息：没有读到必要规格  
 工具：无法执行测试、查看日志、搜索文件  
 约束：没有明确禁止错误行为  
 验证：没有测试或检查机制判断结果是否正确  
```
5. 人类不再只是写代码，而是设计环境、标准和反馈回路。  

``` 
也就是说，工程师的价值会从“亲手完成每一步”转向“让 Agent 在正确的环境中稳定完成任务”。
``` 
## 对我的启发  
  
在 AI 辅助开发中，不能只优化指示文。还要思考：  
  
- 是否给了 AI 足够但不过量的上下文？  
- 是否有明确的输出模板？  
- 是否有可执行的校验方式？  
- 是否有失败后的修正流程？  
- 是否能把常见错误沉淀成规则、脚本或测试？
