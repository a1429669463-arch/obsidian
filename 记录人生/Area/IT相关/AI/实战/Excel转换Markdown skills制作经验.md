# AI 作业设计中的职责划分与 Skill 设计原则

## 1. 基本原则

AI 作业设计的重点，不是让 AI 处理全部内容，而是先明确职责边界。

可以机械判断的内容，应尽量交给脚本、规则或程序处理。  
例如：

- 文件读取；
    
- 格式转换；
    
- 删除线识别；
    
- 图片抽出；
    
- 文本框、吹出的位置取得；
    
- 空白 Sheet 的初步判断。
    

AI 更适合处理脚本难以稳定判断的内容。  
例如：

- 语义判断；
    
- 内容整理；
    
- Markdown 结构整形；
    
- 吹出、文本框的插入位置判断；
    
- 表格和说明文字的关系判断；
    
- 是否属于无关内容的判断。
    

也就是说：

```text
脚本负责机械处理；
AI 负责语义判断。
```

---

## 2. 交给 AI 的判断必须写清楚标准

如果只让 AI “自行判断”，AI 很容易根据上下文猜测。  
这样不仅会增加 token 消耗，也会导致结果不稳定。

因此，凡是交给 AI 判断的内容，都需要尽量写清楚判断标准。

例如在 Excel 转 Markdown 时，如果要让 AI 删除无关内容，就需要说明：

- 什么内容算无关；
    
- 什么内容可以删除；
    
- 什么内容必须保留；
    
- 判断依据是什么；
    
- 不确定时应该保留还是删除。
    

很多判断标准其实只存在于人的经验中。  
如果不把这些经验写出来，AI 就只能靠猜。

比较好的做法是把判断内容分成两类：

```text
机械判断：
- 删除线由脚本识别；
- 图片由脚本抽出；
- 文本框和吹出由脚本输出位置和周边单元格；
- 表格结构由脚本尽量保持原样输出。

AI 判断：
- 判断吹出/文本框应插入到 Markdown 的哪个位置；
- 判断说明文字是否属于表格；
- 判断哪些内容只是 Excel 辅助信息；
- 判断 Markdown 是否需要整形；
- 判断标题、段落、列表、表格是否自然。
```

这样 AI 不是自由发挥，而是在明确规则下辅助判断。

---

## 3. Skill 应该轻量化

Skill 不应该承载所有详细规则。  
它更适合写：

- 作业目的；
    
- 基本手顺；
    
- 输入输出格式；
    
- 何时使用该 Skill；
    
- 需要参考哪些 Rule；
    
- 最低限度的注意事项；
    
- 作业完成后的检查方式。
    

详细规则、例外情况、具体判断标准，不应该全部塞进 Skill 本体中。

原因是：

- Skill 每次调用都会进入上下文；
    
- Skill 太长会增加 token 消耗；
    
- 很多规则不是每次都会用到；
    
- 信息过多会干扰 AI 判断重点；
    
- 经常调用的 Skill 会因此变慢、变贵。
    

因此，Skill 应该像“作业入口”和“手顺说明”，而不是完整知识库。

---

## 4. Rule 应该按需参考

详细规则应该从 Skill 中拆出来，放到独立的 Rule 文件中。

判断某个内容应该写进 Skill，还是拆成 Rule，可以看一个标准：

> AI 每次执行这个 Skill 时，是否一定会用到这部分信息。

如果每次都会用到，就写进 Skill。  
如果不是每次都会用到，就拆成 Rule，按需参考。

例如：

```text
适合写进 Skill：
- Excel 转 Markdown 的基本流程；
- 输出 Markdown 的基本格式；
- 基本检查项目；
- 发生错误时的处理方式；
- 不确定时优先保留内容。

适合拆成 Rule：
- 吹出的插入规则；
- 文本框位置判断规则；
- 图片/流程图插入规则；
- 删除无关内容的规则；
- 特定 Pattern 的表格整形规则。
```

不过，Rule 的按需参考不能完全依赖 AI 自己想起。  
最好由脚本或检测结果触发。

例如：

```text
has_callout = true       → 参考 callout_rule.md
has_textbox = true       → 参考 textbox_rule.md
image_count > 0          → 参考 image_rule.md
need_delete_check = true → 参考 delete_rule.md
```

这样可以避免 AI 漏读规则。

---

## 5. Rule 本身也要写得可执行

Rule 不能只写抽象原则。  
如果只写“删除无关内容”“适当整形”，AI 仍然可能理解偏。

比较好的 Rule 应包含：

- 规则；
    
- 例子；
    
- 反例；
    
- 例外情况；
    
- 不确定时的处理方式；
    
- 检查方法。
    

例如：

```text
规则：
与业务说明、画面项目、SQL、操作步骤无关的临时备注可以删除。

反例：
如果备注中包含业务规则、错误原因、改修理由，则不能删除。

不确定时：
不要删除，保留并标记“要确认”。

检查方法：
最终 Markdown 中不能误删业务规则、SQL、文件路径、操作步骤。
```

这样 AI 才能按照明确标准判断，而不是凭感觉处理。

---

## 6. 需要增加结果检查机制

AI 作业不能只关注“如何生成”，还要关注“如何检查”。

尤其是 Excel 转 Markdown 这种任务，最终结果需要确认：

- 表格列数是否一致；
    
- Markdown 表格是否破损；
    
- 图片链接是否存在；
    
- SQL 是否被 code block 包裹；
    
- 删除线语法是否影响预览；
    
- 吹出/文本框是否插入到对应内容附近；
    
- 是否存在“要确认”标记；
    
- 是否误删重要业务内容。
    

能用脚本检查的部分，应尽量脚本化。  
AI 只处理检查失败或需要语义判断的局部内容。

理想流程是：

```text
脚本生成 Markdown
↓
脚本检查格式问题
↓
AI 处理需要语义判断的部分
↓
人工最终 Review
```

## 7. 以 Excel 转 Markdown 为例

整体结构可以设计为：

```text
Skill：
- 说明整体转换流程；
- 说明先运行泛用脚本；
- 说明根据检测结果参考对应 Rule；
- 说明最终输出 Markdown；
- 说明检查项目和人工 Review。

Rule：
- 删除线处理规则；
- 图片处理规则；
- 流程图处理规则；
- 吹出/文本框插入规则；
- 无关内容删除规则；
- 表格整形规则。

Tool：
- Excel 读取脚本；
- 图片抽出脚本；
- 文本框/吹出检测脚本；
- Markdown 检查脚本。
```

不同情况走不同流程：

```text
无特殊对象：
泛用脚本 → Markdown → 格式检查 → 最小整形

有吹出/文本框：
泛用脚本 → 对象抽取 → 参考对应 Rule → AI 局部整形 → 检查

有图片/流程图：
泛用脚本 → 图片抽出 → 参考图片规则 → AI 局部整形 → 检查
```

---

## 8. 总结

AI 作业设计的核心是分层：

```text
Tool 负责机械处理，返回结果时提供必要信息给Ai；
Skill 负责作业流程；
Rule 负责判断标准；
Check 负责结果验证；
AI 负责语义判断和整形；
人工负责最终确认。
```

能机械处理的，不交给 AI。  
必须交给 AI 的，要提供明确 Rule。  
不是每次都会用到的 Rule，不放进 Skill，而是按检测结果加载。  
最终结果还需要 Check 机制，避免 AI 生成看似合理但无法交付的内容。

这样可以减少 token 消耗，提高作业稳定性，也能让 AI 从“靠猜”变成“按规则工作”。
